# Amazon S3

Amazon Simple Storage Service (S3) is durable object storage for files and data objects held in buckets. Applications use it for user uploads, backups, static assets, logs, data lakes, and event-driven pipelines. S3 separates object storage from compute and relational query processing: applications address objects by bucket and key, and service APIs read or modify object data. A prefix such as `tenant-42/2026/` looks like a folder in many tools but is part of the object key, not a POSIX directory hierarchy.

S3 provides strong read-after-write consistency for object PUTs and DELETEs. That does not make a multi-object workflow transactional or resolve concurrent application writes automatically. If two writers update the same key, the application needs a conflict or versioning strategy. Design keys, metadata, object size, and ownership to support retrieval and lifecycle needs; do not assume a bucket behaves like a relational database or a shared mounted filesystem.

## Object lifecycle and access patterns

Storage classes trade storage price against retrieval latency, availability characteristics, minimum storage duration, and retrieval charges. Use a class based on actual access patterns and recovery objectives, not only the lowest monthly storage price. Lifecycle rules can transition objects between classes or expire them, but test policies against real key prefixes and retention requirements. Objects in archival classes may require a restore operation before access. Versioning preserves prior object versions and can recover from accidental overwrite/deletion, but retained versions consume storage and require lifecycle management.

Multipart upload is appropriate for large objects and improves transfer resilience by splitting upload into parts. Abandoned multipart uploads can incur storage charges, so configure lifecycle cleanup where appropriate. AWS SDK transfer utilities can manage multipart operations; application code still needs cancellation, retries, integrity validation, and cleanup. S3 supports checksums for integrity verification—use the supported mechanism rather than treating an HTTP success code as proof the intended content was stored.

Presigned URLs allow a client to access a specific object operation for a limited time without the application proxying all bytes. Treat them as bearer tokens: anyone possessing a valid URL can use it within its constraints until expiration or other invalidation. Scope the URL to a specific bucket/key, method, and short lifetime, and avoid logging the URL. The server should authorize which user may obtain it, choose an unpredictable or server-owned key, and verify ownership on completion. Do not trust client-supplied filenames, content types, metadata, or size claims; validate actual content and enforce quotas.

## Events, workflows, and consistency

S3 event notifications can invoke supported destinations such as Lambda, SQS, or SNS depending on configuration. Event delivery may be duplicated and ordering is not generally guaranteed for arbitrary key workflows; consumers should be idempotent and use object version identifiers or other durable event identities when needed. A notification can arrive before another part of an application workflow is complete. Design a processing state machine or reconciliation process rather than assuming an event is a transaction commit signal across systems.

For multi-step workflows, write metadata or state to a database and use an outbox/reconciliation pattern when cross-service coordination matters. Objects are good for large immutable payloads; a database is often better for mutable metadata and business invariants. Avoid listing massive prefixes as a substitute for an index on every request. Choose key structure and partitioning based on access patterns, though modern S3 does not require the old random-prefix pattern for request scaling. Measure request rates and use inventory/analytics tools for large-scale catalog work.

## Security and reliability

Block public access at account and bucket levels unless public distribution is explicitly required and reviewed. Use IAM identity policies, bucket policies, and access points to grant least privilege. Bucket policy conditions can enforce TLS, encryption headers, approved principals, or network paths where supported, but verify condition behavior for the actual caller and service integration. Keep S3 Block Public Access enabled by default and use CloudFront or another controlled distribution for public content where appropriate.

S3 encrypts new object data by default with server-side encryption, but compliance may require a specific encryption mode or customer-managed KMS key. KMS key policy and IAM permissions both affect reads and writes; a bucket permission alone may not be sufficient. Key disablement or policy changes can make encrypted objects inaccessible. Enable versioning, replication, Object Lock, and retention controls only to meet defined recovery or immutability requirements. Replication is not a replacement for backup against every deletion or corruption scenario: replicated deletions and versions depend on configuration. Object Lock compliance mode is a strong retention control and must be planned before activation.

Log and audit access when required, restrict access to logs, and monitor policy changes, public-access findings, failed requests, replication status, and lifecycle outcomes. Use CloudTrail data events for object-level auditing when required, recognizing that event volume and cost can be significant. Test restore procedures, including version recovery and cross-account/Region access. Common failures include missing KMS permissions, incorrect bucket-region assumptions, an expired or over-broad presigned URL, CORS misconfiguration, lifecycle deletion of needed data, and retrying an upload with a partially completed multipart state.

## .NET integration and operational tradeoffs

The AWS SDK for .NET provides S3 clients and transfer utilities. Reuse clients safely, use asynchronous streaming APIs, pass cancellation tokens through upload/download operations, and avoid buffering multi-gigabyte objects in memory. Configure retries and timeouts with awareness that a failed response may leave uncertainty about whether an operation completed. Use version IDs, checksums, and conditional requests where the workflow needs concurrency control. For web uploads, presigned direct-to-S3 transfer can reduce application bandwidth and memory pressure, but the application must still authorize, validate, and track the uploaded object.

Keep application data out of logs and telemetry; even object keys can contain personal or sensitive details. Separate buckets or access points by account/environment and data sensitivity where that clarifies policy. Use lifecycle policies for retention and storage-class management, then measure access and restore costs. Interview answers should explain the object/key model, why large files should be streamed or uploaded directly, how access is scoped, and how the application handles duplicate events and data recovery.

S3 costs include stored bytes by class, requests, retrieval, lifecycle transitions, data transfer, replication, and optional KMS requests. Infrequent-access or archival tiers are not automatically cheaper for hot or frequently restored data. Model the entire lifecycle, including restore time and retrieval fees, before moving critical content.

## Application workflows and recovery design

For uploads, separate the control plane from the data plane. The application authenticates the user, checks quota and ownership, allocates a server-controlled object key, and issues a short-lived presigned request. After upload, a trusted backend validates the object’s actual size, checksum, type, and malware-scanning outcome before marking the business record complete. A browser receiving a successful PUT does not mean the file passed policy checks or that a corresponding database row committed. Use a staged state such as `PendingValidation` and reconcile abandoned uploads.

For downloads, authorize access before issuing a narrowly scoped URL or proxying the content. URLs can be copied and are reusable until expiry, so avoid placing them in logs, analytics, or referrer-bearing pages. Consider response headers, cache behavior, and content disposition for untrusted files. If CloudFront is used, design origin access and cache invalidation/TTL intentionally; do not make a private bucket public merely to simplify delivery.

Versioning helps recover from overwrites and deletes, but recovery must identify the intended version and restore it without overwriting newer valid data. Lifecycle policies should cover noncurrent versions and incomplete multipart uploads, not only current objects. Replication can meet cross-Region or account recovery goals, but it introduces replication status, permissions, KMS key, and delete-marker considerations. Define whether recovery must protect against accidental deletion, malicious deletion, regional impairment, or logical corruption—these are different threat scenarios and may need independent controls.

Treat object metadata and tags as part of the application contract. Metadata is set at object creation and changing it can require copying/replacing the object; tags can support classification and lifecycle rules but should not contain secrets. Key naming can reveal tenant identifiers or other sensitive context to operators and logs, so use opaque identifiers where appropriate. Store searchable business attributes in a database or catalog rather than attempting to query arbitrary object metadata at request time.

For multi-tenant applications, authorization must bind the authenticated tenant to the server-generated object key; accepting a bucket/key pair from a client without checking ownership creates an insecure direct-object-reference risk. A presigned upload should not let a caller overwrite a different tenant’s object or choose a public ACL. Validate required encryption and metadata at the bucket/policy or service boundary where possible, then verify the completed object before exposing it. Keep quarantine and published content paths distinct when files require scanning or moderation.

For backups, define consistency across the source and object. Copying an individual file while a database transaction is in progress may not produce a recoverable system state. Track manifest, checksum, timestamp, and source version so a restore can be validated. Test not only retrieval of one sample object but restoration of a representative dataset, including access policies and decryption keys. Replication lag, lifecycle transitions, and archived-object restore time should be included in the documented recovery plan.
